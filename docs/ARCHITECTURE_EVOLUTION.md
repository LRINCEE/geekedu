# GeekEdu 架构演进与重构纪实：万级并发下的高可用课程列表设计

## 核心背景
在线教育平台 (GeekEdu) 的首页课程列表 (`ListCourses`) 是典型的**读多写少**且**高并发**的场景。在单次拉取大数据量（如 `pageSize=1000`）时，传统的直接查库方案面临严峻的性能挑战。为了打造一份具备大厂技术深度的简历级项目，我们对此接口进行了一次深度的架构演进。

## 演进故事：从裸奔的 MySQL 到教科书级的高并发架构

### 阶段一：纯 MySQL 的裸奔与雪崩危机
**最初的问题**：
最开始，我们使用 GORM 的 `db.Find(&courses)` 直接查询 MySQL。
在 17,000 条课程数据的背景下，当我们使用 `hey` 工具发起 100 并发、5000 次请求（单次拉取 1000 条数据）的压测时，系统几乎崩溃。
- **思考过程**：大量的并发请求直接穿透到 DB，不仅产生了全表扫描的磁盘 I/O 瓶颈，而且默认的 `SELECT *` 把长文本（如课程描述）也查了出来，瞬间耗尽了 MySQL 的连接池和 Go 的内存。
- **压测数据**：QPS 仅为 **320**，平均延迟高达 **297ms**，P99 延迟突破 **852ms**。
- **解决方案**：
  1. **SQL 优化**：将 `SELECT *` 改为明确的 `.Select("id", "title", "price", "cover_key")`，利用覆盖索引并减少内存拷贝。
  2. **引入缓存**：引入 Redis，采用标准的 Cache-Aside（旁路缓存）模式，查不到再查库并回写。

### 阶段二：引入 Redis (JSON) 后的 CPU 刺客
**解决了之后发生的新问题**：
引入 Redis 后，我们将查询结果用 `json.Marshal` 序列化存入 Redis。数据库确实保住了，没有再出现连接池打满的 500 错误。但是，当我们再次压测（拉取 1000 条数据的大载荷）时，发现 QPS 提升并不符合“内存级速度”的预期。
- **思考过程**：通过压测对比发现，在微小载荷（如 10 条数据，1.7KB）下，JSON 速度尚可（QPS 能破万，因为瓶颈在网络调度）。但当数据量拉大到 1000 条时，Go 标准库的 `encoding/json` 需要通过大量的**反射 (Reflection)** 来解析庞大的结构体数组。这产生了极其可怕的 CPU 计算开销和海量的临时对象，导致 GC（垃圾回收）压力骤增，拖慢了整体响应。
- **压测数据**：QPS 提升至 **1156**，平均延迟降至 **82.5ms**。（虽然挡住了 DB，但 CPU 成了新瓶颈）。
- **解决方案**：抛弃 JSON，改用 gRPC 原生的 **Protobuf** 二进制序列化（`proto.Marshal`）。Protobuf 基于预编译文件，无需反射，体积更小，解析速度呈指数级提升。此外，这也避免了 gRPC 框架底层的“双重序列化”陷阱（避免 Redis JSON -> Go 结构体 -> gRPC Protobuf 的重复转换）。
- **二次压测数据**：切换 Protobuf 后，QPS 跃升至 **1821**，平均延迟降至 **52.5ms**。吞吐量比 JSON 提升了近 **60%**！

### 阶段三：致命的缓存击穿 (Cache Stampede)
**继续深挖的隐患**：
虽然 QPS 上去了，但我们思考了一个极端场景：如果这 1000 个并发请求到达时，Redis 里的缓存**刚好过期了**，会发生什么？
- **思考过程**：在这瞬间，1000 个并发请求会同时发现 Redis 返回 `redis.Nil`（未命中），然后这 1000 个 Goroutine 会在同一毫秒内全部砸向 MySQL 执行复杂的查询语句。这叫“缓存击穿”，会导致数据库瞬间宕机。
- **解决方案**：引入了 Go 官方的防并发击穿神器 `golang.org/x/sync/singleflight`。
  - 我们用 `sg.Do(cacheKey, func() {...})` 包裹了查库逻辑。
  - 当缓存失效时，即使有 100 个并发请求同时涌入，Singleflight 也只会放行**第 1 个**请求去查 MySQL，其余 99 个请求在门外挂起等待。等第 1 个请求查完并写回 Redis 后，将这 1 份结果直接分享给那 99 个等待的请求。
  - **结果**：无论并发多高，同一时刻对同一个 CacheKey，永远只有 1 次数据库查询。在开启 `bypassRedis=true` 的极限断言测试中，我们证明了 Singleflight 甚至能把纯 DB 查询的 QPS 维持在 8000+，完美掩盖了底层的耗时。

### 阶段四：防患未然的缓存雪崩 (Cache Avalanche)
**最后一块拼图**：
缓存击穿是针对“单条热点数据”，那如果是“海量数据同时过期”呢？比如系统在半夜统一生成了 1000 页的课程缓存，统一设置了 5 分钟（`5 * time.Minute`）的过期时间。5 分钟后，这 1000 页缓存将同时失效，再次引发灾难。
- **思考过程**：绝对不能让大批量的缓存拥有完全一致的生命周期。
- **解决方案**：引入 **TTL 随机抖动 (Jitter)**。
  ```go
  // 基础时间 5 分钟 + 0到59秒的随机抖动
  jitter := time.Duration(rand.Intn(60)) * time.Second
  expiration := 5*time.Minute + jitter
  ```
  通过这简单的一行代码，我们将原本集中在同一秒爆发的过期潮，均匀地打散到了 1 分钟的时间窗口内，彻底消除了缓存雪崩的隐患。

## 总结：数据说话的架构跃迁
| 架构阶段 | 序列化方式 | 防护机制 | QPS (100并发/大载荷) | Avg 延迟 | 核心瓶颈 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1. 纯 MySQL 裸奔 | 无 | 无 | 320 | 297.0ms | DB 磁盘 I/O、内存拷贝 |
| 2. Redis 缓存 | JSON | 无 | 1156 | 82.5ms | CPU 反射开销、GC 压力 |
| 3. Redis 缓存 | Protobuf | 无 | 1821 | 52.5ms | 网络带宽、调度极限 |
| 4. 高可用终极形态 | Protobuf | Singleflight + TTL Jitter | **1821+** | **<50ms** | 系统坚如磐石，无明显短板 |

> **技术沉淀**：
> 真正的企业级优化，绝不是简单地“加个 Redis”。而是要在数据链路的每一个节点（查库字段、序列化 CPU 开销、高并发边界条件）进行严密的推演。从 `SELECT *` 到覆盖索引，从 JSON 反射到 Protobuf 二进制流，再到 Singleflight 防击穿与随机 TTL 防雪崩。这是一次以数据为导向、从物理层到逻辑层的教科书式性能重构。

**最初的问题**：
在微服务间通信时，Logic Server 返回了业务错误，但 Web Server 只能通过 `st.Message() == "user not found"` 这种极其脆弱的硬编码字符串匹配来判断错误类型。一旦底层修改了错误文案，上层路由直接崩溃。

**解决过程**：
我们需要透传包含业务错误码（如 `10001`）和 HTTP 状态码的结构化错误。
我们重构了错误处理机制，将自定义的 `errcode.ErrCode` 对象序列化为 JSON 字符串，然后作为 Metadata 塞入 gRPC 的 `status.Error(codes.Unknown, jsonStr)` 中。在 Web Server 的拦截器中，再将其反序列化恢复为原始对象。这彻底消灭了字符串匹配反模式，实现了企业级的错误码透传。

## 故事三：生产级防御 —— 结构化日志与限流器

**最初的问题**：
Gin 框架默认的日志是控制台纯文本，无法进行机器解析，且不支持日志切割，时间久了会把服务器磁盘撑爆。同时，任何恶意用户都可以通过疯狂调用接口来耗尽我们的服务器资源。

**解决过程**：
1. **日志重构**：引入了 Uber 开源的 `Zap` 替换 Gin 默认 logger，实现 JSON 格式的结构化日志；配合 `Lumberjack` 实现了按大小、时间自动轮转（Log Rotation）。
2. **接口限流**：基于令牌桶算法（Token Bucket）编写了限流中间件。
*发生的新问题*：限流器开启后，我们自己的 k6 压力测试也被拦截了，返回了大量 HTTP 429 Too Many Requests。
*最终方案*：我们在配置中加入了测试环境旁路（Bypass）开关，在压测时动态关闭限流，保证了防御机制与性能测试的兼容。

## 故事四：优雅与痛点并存的 API 文档 —— 泛型与 Swagger

**最初的问题**：
前端同学抱怨没有标准的接口文档。我们决定使用 `swaggo/swag` 根据代码注释自动生成 OpenAPI 文档。

**解决过程**：
在给每个接口加注释时，遇到了“DTO 爆炸”的问题：由于 Swagger 必须知道确切的返回结构，而我们的返回通常是 `{code, msg, data}`。如果不用泛型，我们就必须为课程、视频、订单分别定义 `ListCourseResponseDTO`、`GetVideoResponseDTO` 等无数个冗余结构体。

*发生的新问题与解决*：
我们大胆引入了 Go 1.18 的泛型，重构了全局响应体 `Response[T any]`。但在执行 `swag init` 时，接连遇到了三个坑：
1. **版本冲突**：本机安装的 swag 命令行工具与 `go.mod` 中的库版本不一致，报 `LeftDelim` 模板错误。我们通过 `go get -u` 统一升级解决。
2. **幽灵报错**：IDE 中修改了代码，但 swag 始终报错找不到类型。最终发现是因为文件未保存到磁盘，CLI 工具读的是旧代码。
3. **结构体命名歧义**：gRPC 生成的 pb 文件中，课程数组的元素叫 `CourseItem` 而不是 `Course`，导致 swag 解析失败。修正注释后完美生成了嵌套的可视化 JSON 文档。

## 故事五：走向整洁架构 —— 彻底的解耦与单元测试

**最初的问题**：
当我们准备写单元测试时，发现 `Logic Server` 的业务逻辑（Service 层）被死死绑在了基础设施上：它直接调用了 `dao.RedisClient` 全局变量，直接调用了 `ossutil` 包级别函数，依赖了具体的 `Dao` 结构体，甚至密码校验直接硬编码了 `bcrypt`。这导致我们根本无法在没有真实 MySQL/Redis/OSS 的环境下运行任何单元测试。

**解决过程（重构之路）**：
1. **第一阶段（基于结构体的依赖注入）**：我们抛弃了在 Service 内部直接 `NewDao()` 的做法，改成了通过构造函数 `NewUserServiceServerWithDAO(dao)` 将依赖传进去。引入了 `sqlmock` 拦截底层的 GORM 查询。
2. **第二阶段（发现残留毒瘤）**：我们发现即便隔离了 DB，代码依然在跑真实的 `bcrypt` 哈希，且 `RedisClient` 依然是全局强耦合的。
3. **终极形态（面向接口编程）**：
   - 我们在 `dependencies.go` 中定义了纯粹的接口：`CourseRepository`、`Cache`、`ObjectStorage`、`PasswordManager`。
   - 编写了 `RedisAdapter` 和 `OSSAdapter` 去实现这些接口。
   - 将 `CourseService` 等所有服务内部的字段从具体实现全部改为接口。
   - 在 `main.go` 的最顶层进行生产环境依赖组装。

*发生的细节问题*：
在解耦时，我们发现 `CourseService` 内部用于防击穿的 `singleflight.Group` 是一个全局变量。在并行跑多个单测时，不同测试用例间的锁状态会互相污染（Flaky Tests）。
*最终解决*：我们将 `singleflight.Group` 作为实例字段移入了 `CourseServiceServer` 结构体内部，将其生命周期与 Service 实例绑定，彻底消除了全局状态污染。

至此，GeekEdu 实现了真正的核心业务逻辑与基础设施分离（Clean Architecture），我们可以用 0.1 秒跑完所有的核心业务单测，项目正式具备了企业级的代码质量。
